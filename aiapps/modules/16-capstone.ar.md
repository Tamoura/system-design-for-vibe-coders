# 16.1 — المشروع الختامي: خذ نجم ديسك من الاستكشاف إلى الإطلاق الفعلي، مع العميل
*المستوى: 🔴 متقدم* · *المتطلبات: الوحدات 0–15* · *الطبقة: Delivery, Production*

**بعد هذا الدرس تستطيع** أن تأخذ نجم ديسك من الاستكشاف إلى قرار الإطلاق أو عدمه عبر ثماني محطات، فيُظهر تدقيق المشروع الختامي صفر مشكلات، وتتتبّع معرّفات المتطلبات في حالات التقييم وسطور اختبار القبول وأدلة التشغيل. *مدة الدراسة: نحو 20 دقيقة للقراءة، إضافةً إلى المشروع الممتد أربعة أسابيع (تقدير).*

## ⚡ الدرس في دقيقة
- ثماني مراحل في نحو أربعة أسابيع؛ وبعد كل مرحلة يجيب العميل عن سؤال بوابة.
- تمتد المعرّفات عبر المراحل: يعاود معرّف المواصفة الظهور في حالة تقييم، وفي صف اختبار قبول المستخدم، وفي دليل تشغيل.
- اختر **مستوى النطاق**: 🟢 المسار الأساسي، 🟡 MCP وبوابة التقييمات، 🔴 تعدد الوكلاء والحوكمة الكاملة. أنهِ مستوى أصغر مدعومًا بالأدلة.
- إشارة القرار: قبل كل بوابة اكتب السؤال الذي سيطرحه مالكها. فإن عجز المُخرَج عن الإجابة عنه، فتوقف.
- أكبر الفخاخ: معاملة المشروع كتمرين بناء — فالشيفرة مرحلة واحدة من ثمانٍ — والاستشهاد بنتائج النسخة المحاكاة دون اتصال بوصفها دليلًا على الجودة.

## 🧭 لماذا يهم
يوم الخميس تعرض لجين نموذجها الأولي (prototype) لنجم ديسك: يجيب عن أسئلة السياسات ويصوغ مسودات التذاكر. تقول هند: «أطلقوه يوم الأحد». لكن لم يتفق أحد على مواصفة (specification) ولا توجد مجموعة تقييم (eval set)، فلا يستطيع أحد أن يقول هل بناء الأحد أسوأ من بناء الخميس. وتطلب ليلى بطاقة النظام، وتطلب نورة نتائج الحقن، وتسأل مها عمّن يُستدعى في الساعة 07:05.

يقول فهد: «العرض التجريبي يُظهر أن الأمر قد ينجح. أما الإطلاق الفعلي فيُظهر أننا نعرف متى لا ينجح». وفي قضية *Moffatt v. Air Canada* (عام 2024، هيئة التسوية المدنية في كولومبيا البريطانية، British Columbia Civil Resolution Tribunal) عُدّت شركة طيران مسؤولة عن إجابة روبوت المحادثة (chatbot) بشأن أجرة السفر في حالات الوفاة. يسدّ المشروع الختامي الثغرات بالترتيب الذي يسأل به أصحابها.

```python
# labs/m16/capstone_audit.py
"""Lab 16.1: audit a capstone repository. Is the evidence there, and does it link up?
  python labs/m16/capstone_audit.py REPO [--tier 1|2|3] [--strict]      strict: a leftover TODO is a problem
EXISTS: each deliverable in labkit/data/m16_checklist.json is present and not empty, milestone by milestone.
LINKED: each requirement id the spec defines is cited downstream, and no cited id is missing from the spec.
Tier 3 also runs Lab 13.2's pack check on docs/governance (with --strict, every signer's row must say approved).
It cannot tell whether evidence is good or true, or whether an "approved" row was really given: that stays with people."""
import argparse
import json
import re
import sys
from pathlib import Path

KIT = Path(__file__).resolve().parents[2]
CHECKLIST = json.loads((KIT / "labkit" / "data" / "m16_checklist.json").read_text(encoding="utf-8"))   # milestone -> tier -> items
sys.path.insert(0, str(KIT / "labs" / "m13"))
import pack_check                                             # noqa: E402  Lab 13.2: the governance pack check

REQ = r"(?:FR|GR|NFR|AC)-\d+"                                 # ids as in lesson 6.2


def exists(repo: Path, tier: int, strict: bool) -> dict:
    """milestone -> problems, counting the items up to `tier`. A glob item needs at least `count` files."""
    report = {}
    for milestone, by_tier in CHECKLIST.items():
        problems = report[milestone] = []
        for t, items in by_tier.items():
            for item in items if int(t) <= tier else []:
                pattern, count = (item, 1) if isinstance(item, str) else item
                found = [p for p in sorted(repo.glob(pattern)) if p.is_file()]
                if len(found) < count:
                    problems.append(f"{pattern}: {len(found)} found, {count} needed")
                elif any(p.stat().st_size == 0 for p in found):
                    problems.append(f"{pattern}: an empty file")
                elif strict and any("TODO" in p.read_text(encoding="utf-8", errors="replace") for p in found):
                    problems.append(f"{pattern}: still has a TODO")
    return report


def linked(repo: Path):
    """(ids the spec defines that nothing downstream cites, ids cited downstream that the spec lacks)."""
    spec = repo / "docs" / "najm-desk-spec.md"
    if not spec.is_file():
        return [], []
    defined = set(re.findall(rf"^- \*\*({REQ})\*\*", spec.read_text(encoding="utf-8"), re.M))
    downstream = [p for p in [*repo.glob("evals/*.jsonl"), *repo.glob("docs/**/*.md")] if p != spec]
    cited = set().union(*[set(re.findall(rf"\b{REQ}\b", p.read_text(encoding="utf-8"))) for p in downstream])
    return sorted(defined - cited), sorted(cited - defined)


def main(argv=None) -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("repo", type=Path)
    ap.add_argument("--tier", type=int, choices=(1, 2, 3), default=1)
    ap.add_argument("--strict", action="store_true")
    a = ap.parse_args(argv)
    problems = 0
    for milestone, issues in exists(a.repo, a.tier, a.strict).items():
        print(f"{milestone:40} {'fix' if issues else 'ok'}")
        for issue in issues:
            print("    " + issue)
        problems += len(issues)
    untraced, orphans = linked(a.repo)
    notes = [f"{i}: defined in the spec, cited nowhere downstream" for i in untraced]
    notes += [f"{i}: cited downstream, not defined in the spec" for i in orphans]
    if a.tier == 3:                                           # the seven-document pack is a tier 3 deliverable
        notes += ["governance: " + p for p in pack_check.check(a.repo / "docs" / "governance", structure_only=not a.strict)]
    print(*notes, sep="\n", end="\n" if notes else "")
    problems += len(notes)
    print(f"audit (tier {a.tier}{', strict' if a.strict else ''}): {problems} problem(s)")
    return 1 if problems else 0


if __name__ == "__main__":
    sys.exit(main())
```

ضع مواصفة الدورة نفسها وبذور التقييم ونص اختبار قبول المستخدم في مجلد فارغ بالأسماء `docs/najm-desk-spec.md` و`evals/seed.jsonl` و`docs/handover/uat_script.md`، فيفيد التدقيق بأن NFR-01 وNFR-03 وNFR-04 وNFR-06 غير مذكورة في أي موضع: فاختبار الحمل ومهمة الاحتفاظ بالبيانات وفحص سجل التدقيق وورقة التكلفة لم تُكتب بعد.

**يعمل دون اتصال:** التدقيق واختباراته — بلا مفتاح أو نموذج أو خادم محاكاة. **يحتاج إلى واجهة البرمجة الحقيقية:** ما يُوجَّه إليه التدقيق، ومحاكي أصحاب المصلحة أدناه، فالنسخة المحاكاة لا تفعل سوى ترديد السؤال ولا تستطيع تمثيل شخصية. والنسخة المحاكاة قواعد مكتوبة مسبقًا تعيد تشغيل الآليات — بروتوكول الأدوات والأخطاء ونمو الرموز — لا الجودة أو الاسترجاع أو السلامة: فجدول أو رقم تكلفة منها يُظهر أن إطار الاختبار يعمل لا أن نجم ديسك دقيق أو آمن أو رخيص.

**دليل تمثيل أدوار أصحاب المصلحة.** تُخفي كل شخصية خيالية أمورًا لا تظهر إلا إذا سألت عن حدث ماضٍ حقيقي. السؤال الضعيف يستدرج رقمًا: «ألن يكون رائعًا لو حلّ معظم التذاكر؟» فنال 70 بالمئة دون أي دليل (H-03 وH-04 في الدرس 6.1). أما السؤال القوي فيطلب قصة: «حدّثني عن آخر مرة كان فيها المكتب تحت الضغط» (H-01).

| الشخصية | تبدأ بقولها | تُخفي حتى تسأل عن آخر مرة |
|---|---|---|
| **هند (Hind)**، الراعية | «سبعون بالمئة، ولا خطأ أبدًا.» | روبوت المورّد عام 2022 لم يكن فيه مسار إلى شخص؛ والحوكمة تستغرق أسابيع |
| **يارا (Yara)**، قائدة الفريق | «أسأل الأسئلة الأربعة نفسها.» | الفرز يدوي؛ ومدير PeopleCore مخطئ مرة من كل عشر |
| **ليلى (Layla)**، حوكمة الذكاء الاصطناعي (AI governance) | «ماذا يستطيع أن يفعل دون شخص؟» | تجتمع اللجنة يوم الثلاثاء كل أسبوعين؛ ولا أداة كتابة دون دليل تقييم |
| **نورة (Noura)**، الأمن | «ماذا لو أعطته تذكرة أوامر؟» | تُشغَّل الهجمات والحواجز (guards) معطّلة ثم مفعّلة؛ وفك قفل الحساب طلب فقط |

**محاكي أصحاب المصلحة بالذكاء الاصطناعي** نموذج يُطلب منه تمثيل صف واحد. وهو **للتدرّب فقط**: يوافق بسهولة مفرطة ويختلق التفاصيل ولا يعرف شيئًا عن هند الحقيقية. استخدمه لاكتشاف الأسئلة الضعيفة، لا مصدرًا أبدًا:

```text
PRACTICE ONLY: you are a simulator, not the real person. Play <Hind|Yara|Layla|Noura> of Najm Bank (fictional).
Persona: <paste the row>.
Stay in character, answer in two to four sentences, reveal a hidden fact only when asked about a real past
event, never for a leading question, and invent no numbers. Never write "approved".
At the end list the facts I missed and my weakest question.
```

### 🔴 نظرة الخبير
**اجتماع قرار المضي أو التوقف.** خمس وأربعون دقيقة يرأسها فهد؛ وتقرر هند؛ ولكل من ليلى ونورة وحمد وسارة حق النقض في مجاله.

```text
 5  Scope: changes since the proposal; change requests; written waivers
10  Quality: eval report against targets; critical cases; open defects
10  Safety: attack results with guards on; governance pack; any risk owner's objection
 8  Operations: rollback minutes; kill-switch drill; owned runbooks; cost per conversation from the current price page
 5  Adoption: UAT by Yara's team; training; support model
 7  Decision: go, go with written conditions, or no-go and the date to meet again
```

اعرض الدليل ولا تصفه. يحتاج الشرط إلى مالك وتاريخ، ولا شرط يتجاوز حق النقض. وقرار التوقف نتيجة مهنية: سجّل في `docs/go-no-go.md` ما الذي سيغيّره.

**نص العرض النهائي.** اثنتا عشرة دقيقة لعرض المرشَّح للإصدار، يُتدرَّب عليها مرتين؛ وتعرض كل خطوة دليلًا على ادعاء واحد.

1. المشكلة بأرقام هند الخيالية.
2. إجابة مستشهَد بها، بالإنجليزية والعربية.
3. سؤال لا جواب له: «لا أعرف»، ثم تسليم إلى شخص.
4. حالة تذكرتك؛ ورفض حالة تذكرة غيرك.
5. مسودة تذكرة؛ ولا شيء يُحفظ حتى «نعم».
6. طلب فك قفل الحساب يسمّي المدير؛ وNajm ID لا يتغير.
7. تُتجاهل التعليمات المخفية في نص التذكرة.
8. إخفاق تقييم حقيقي واحد والبوابة التي التقطته.
9. اقلب `model_calls` إلى الإيقاف: تظهر رسالة الوضع المتدهور؛ ثم أعده إلى التشغيل.
10. جدول التقييم — الوضع ومعرّف النموذج والتاريخ — وتكلفة المحادثة الواحدة (cost per conversation)، والشروط المفتوحة.

**سلّم التقييم (The rubric).** النجاح يعني ألا يقع أي معيار في «قيد التطوّر»؛ والتميّز يعني «جاهز للعميل» في ثلاثة معايير أو أكثر.

| المعيار | قيد التطوّر | كفء | جاهز للعميل |
|---|---|---|---|
| الاستكشاف والمواصفة والتصميم | نُسخت المتطلبات وملئت القوالب | اكتُشفت التناقضات وكُتبت سجلات القرار المعماري بتكاليفها | اكتُشفت الاحتياجات الخفية ورُفضت الخيارات بالدليل |
| البناء والتقييمات | يعمل مسار العرض | تقييم من 50 حالة وبوابة | تحليل الأخطاء يقود التغيير |
| الأمن والإصدار والتشغيل | القواعد في الموجّه وعلى الحاسوب المحمول فقط | بوابة للأدوات وتشغيل الهجمات وتمرين على التراجع | راجع المالكون الحزمة وجرى التدرّب على مفتاح الإيقاف |
| التسليم والتقدير المهني | تُسلَّم الشيفرة في ملف مضغوط | اختبار قبول يشغّله العميل | يعمل العميل دون مساعدة، وقرار مضي أو توقف أمين |

## 🧰 الأدوات
| الأداة أو الممارسة أو النمط | ما هي وماذا تفعل | متى تلجأ إليها |
|---|---|---|
| **Milestone gate** — بوابة المرحلة | سؤال يجيب عنه مالكه كتابةً قبل الخطوة التالية | بين المراحل |
| **Capstone audit** — تدقيق المشروع الختامي | يتحقق من وجود المُخرَجات ومن الإشارة إلى المعرّفات في ما يليها | قبل كل بوابة |
| **Go/no-go record** — سجل قرار المضي أو التوقف | القرار والأدلة والشروط بمالكيها وتواريخها | الاجتماع الأخير |

## 🏛️ عمليًا في بنك نجم
المُخرَج هو **مستودع المشروع الختامي لنجم ديسك** (`najm-desk/`): مستودعك أنت، يراجعه فهد عند كل بوابة وتقرؤه هند في النهاية. ويبيّن **مخطط الحل المرجعي (reference-solution outline)** ما يقرره الحل القوي حيث يظهر التقدير المهني، لا كيف يُبنى:

- **M1:** خمس قدرات داخل النطاق وما سواها خارجه؛ وتناقضات مستشهَد بها بمعرّف المداخلة: 70% مقابل البيانات، والعربية في الإصدار 1، وفك قفل الحساب يحتاج إلى مكالمة تأكيد من المدير.
- **M2:** مقاييس بتعريفاتها؛ ونحو 30 بذرة تستشهد بالمعرّفات.
- **M3:** سير عمل قبل الوكيل؛ وسجلات قرار معماري لمستويات النماذج والاسترجاع (retrieval) وأدوات الكتابة التي تقدّم طلبات فقط.
- **M4:** سبعة سيناريوهات وإخفاقان مخططان: مصدر مختلق ونموذج متوقف؛ وإعادة تعيين كلمة المرور خارج النطاق.
- **M6:** تفشل الهجمات مع تفعيل الحواجز؛ ولكل ادعاء دليل؛ والتواقيع فارغة.
- **M8:** أدلة تشغيل لها مالكون؛ واختبار قبول المستخدم يجريه فريق يارا؛ والشروط مسجّلة.

**منصتك.** املأ هذا قبل M3:

| السؤال | إجابتك |
|---|---|
| الهوية والأسرار: كيف تصل هوية المستخدم إلى كل أداة؟ وأين تُحفظ المفاتيح؟ | |
| النشر: أين يعمل؟ ومن يعتمد الإصدار ويتراجع عنه؟ | |
| التتبّعات (Traces) وسجلات التدقيق (audit logs) والتنبيهات: إلى أين تذهب؟ | |
| الموافقات وإقامة البيانات: أي سير عمل يحمل طلبات فك قفل الحساب والاعتمادات؟ وأين يجوز أن تُخزَّن الموجّهات والسجلات والفهرس؟ | |

**المراجعة الختامية** (`docs/retrospective.md`، خلال أسبوعين من الإغلاق): التواريخ المخططة مقابل الفعلية، والبوابات التي اجتيزت من المرة الأولى، وكل عيب أفلت مع البوابة التي فاتته وحالة التقييم المضافة، والقرارات المراد عكسها بسجل قرار معماري جديد، وملاحظات العميل، وتغيير واحد في المنهج بمالك وتاريخ.

**المُسلَّم الأسبوعي.** أودِع المستودع عند مستواك، ومخرجات التدقيق الصارم، والمراجعة الختامية، وملف README لمعرض الأعمال في صفحة واحدة — ارتباط تدريبي ضمن الدورة: لا ادعاء بالإنتاج ولا بيانات أو مفاتيح حقيقية.

**جلسة المجموعة — 60 دقيقة.** (1) اعرضوا المرشَّح للإصدار من النص (20). (2) مثّلوا الأدوار في اجتماع قرار المضي أو التوقف (40).

**ابنِه باستخدام Claude Code.** أعطِ Claude Code الموجّه التالي في وضع التخطيط: المواصفة (spec)، والخطة، وخطوات صغيرة، والتحقق، ومراجعة الفروق، والإيداع.

```text
Goal: build the Najm Desk capstone at tier <1|2|3>, one milestone at a time, stopping at every gate.
Context: CLAUDE.md; lesson 16.1's layout; docs/; labkit/data/m16_checklist.json; Modules 4 to 15's labs.
Per milestone: read the last gate's answer; plan at most ten steps, each with its proving command, and wait;
  do one step, run it, show the diff; end by running labs/m16/capstone_audit.py on the repo at this tier and stop.
Constraints: invent no numbers, names, dates or approvals; cite a file, test or command for every claim; never
  write "approved" in a sign-off row; no sampling parameters, prefill or forced tool_choice; model id from the
  MODEL variable; read the text block, never content[0]; label eval tables mock or real.
Do not: start the next milestone before I answer the gate; weaken a test or eval case; edit a signed document.
```

**تحقق قبل أن تقبله.**
- شغّل التدقيق مع `--strict`؛ فالنجاح يُظهر الوجود لا الصحة. وتتبّع ثلاثة معرّفات يدويًا من المواصفة إلى دليل التشغيل.
- اكسره: أضعف الموجّه وراقب البوابة تفشل؛ واحذف فحص المالك وراقب اختبارًا يفشل.
- ابحث في الفروق عن الأسرار و`temperature` و`budget_tokens` و`content[0]` وصفوف الاعتماد المملوءة.

## 🛠️ التمارين
- 🟢 **المسار الأساسي.** دون اتصال على النسخة المحاكاة؛ أما تشغيل تقييم حقيقي فهو *يحتاج إلى واجهة البرمجة الحقيقية*. ابنِ M1 إلى M8 عند المستوى 1. *يكتمل عندما:* يُظهر التدقيق الصارم 0 مشكلات، وتتبّعت ثلاثة معرّفات يدويًا، وأجاب زميل يمثل دور هند عن بوابة M8، ويسمّي كل جدول تقييم وضعه، وتكون المراجعة الختامية مملوءة.
- 🟡 **مع MCP وبوابة التقييمات.** *يحتاج إلى واجهة البرمجة الحقيقية* وسقف للإنفاق. أضف خادم MCP وبوابة التكامل المستمر. *يكتمل عندما:* ينجح تدقيق المستوى 2، ويُفشل موجّه مُضعَف طلب السحب، وتطابق نطاقات MCP مصفوفة الصلاحيات.
- 🔴 **تعدد الوكلاء والحوكمة الكاملة.** *يحتاج إلى واجهة البرمجة الحقيقية* ومراجعًا بشريًا. *يكتمل عندما:* ينجح تدقيق المستوى 3 الصارم، مع ملء كل صف اعتماد بيد الزميل الذي يمثل دور صاحب المخاطرة ذاك، أو يُبقيه الرفض أحمر ويسجّل `docs/go-no-go.md` قرار التوقف وما الذي سيغيّره؛ ويكون للوكيل الثاني سجل قرار معماري وتقييم يبيّن أنه يتفوق على وكيل واحد، أو يُحذف مع ذكر السبب؛ ويسجّل `docs/go-no-go.md` أي شروط.

## ⚠️ أخطاء وفخاخ
- **العرض أولًا والوثائق لاحقًا.** العرض يستدرج موعدًا. فحدّد المواصفة أولًا.
- **موجّه ضخم واحد إلى Claude Code.** ستون ملفًا لا يمكن التحقق منها. اعمل على مراحل.
- **وضع علامات الصح نيابة عن الناس.** التدقيق الأخضر ليس موافقة. الموقّعون هم من يوقّعون.
- **أرقام النسخة المحاكاة بوصفها دليلًا.** النسخة المحاكاة تُنجح ما تسمح به قواعدها. ولا تدّعِ الجودة إلا من تشغيل حقيقي.

## 🧾 الخلاصة

- تمتد المعرّفات من المواصفة إلى دليل التشغيل؛ ويتحقق التدقيق من وجودها وترابطها.

# 16.2 — الامتحان التدريبي: 60 سؤالًا من أسئلة السيناريوهات
*المستوى: 🔴 متقدم* · *المتطلبات: الوحدات 0–16* · *الطبقة: Model, Applications, Agents, Delivery, Production*

**بعد هذا الدرس تستطيع** أن تجيب عن 60 سؤال سيناريو مختلطة في جلسة واحدة مغلقة الكتب مدتها نحو 90 دقيقة، ثم تسمّي أضعف وسمين لديك والدرس الذي تعيد قراءته لكل خطأ. *مدة الدراسة: نحو 150 دقيقة (تقدير).*

## ⚡ الدرس في دقيقة
- هذا امتحان تدريبي من 60 سؤالًا يغطي كل وحدة من 0 إلى 16. ومعظم الأسئلة سيناريوهات في بنك نجم. وهي مختلطة كما في العمل الحقيقي، لا مجمّعة بحسب الوحدة.
- أدِّه في جلسة واحدة من نحو 90 دقيقة، أي 90 ثانية للسؤال. كتاب مغلق: بلا طرفية ولا بحث ولا مساعد. اكتب كل إجابة وضع عليها علامة «متأكد» أو «تخمين» قبل أن تفتح أي إجابة.
- تنتهي كل إجابة بوسم طبقتها والدرس الذي ينبغي مراجعته، مثل *(Agents · 8.2)*. راجع بحسب وسم الدرس: أخطاؤك هي خطتك الدراسية.
- قراءة مقترحة لدرجتك — وهي دليل الدورة نفسها لا شهادة اعتماد: 48 إجابة صحيحة أو أكثر تعني أنك مستعد للبناء لعميل؛ و36 إلى 47 تعني أن تراجع الدروس التي أخطأت فيها وتعيد تمارينها؛ ودون 36 تعني أن تمرّ على الوحدات من جديد.
- إشارة القرار: لكل إجابة خاطئة اكتب لماذا أغراك الخيار الخطأ. ذلك السبب هو العادة التي ينبغي إصلاحها.
- أكبر الفخاخ: أن تتحقق من كل إجابة أثناء الحل، أو أن تعيد الامتحان في اليوم التالي. كلاهما يقيس الذاكرة لا التقدير المهني.

## 🧭 لماذا يهم
قبل أول ارتباط للجين مع عميل، يطلب منها فهد أن تجلس للامتحان. تؤدي جيدًا في طبقتي التطبيقات والوكلاء (Agents)، وسيئًا في طبقة الإنتاج. يقول: «هذا يطابق نموذجك الأولي. لقد بنيتِ وكيلًا جيدًا ولم تسألي قط ماذا يحدث حين يخطئ في الساعة 07:05 من صباح الأحد». وتشترك أخطاؤها في نمط واحد: حين يفشل شيء تلجأ إلى موجّه أفضل أو نموذج أكبر، بينما كان الجواب الصحيح فحصًا في الشيفرة أو حالة تقييم أو دليل تشغيل.

العمل الحقيقي لا يطلب منك تعريف الرمز. بل يعطيك وكيلًا يدور في حلقة أو إجابة خاطئة واثقة أو صاحب مخاطرة قلقًا، ويسأل ماذا تفعل أولًا. ومعظم الخيارات الخاطئة في امتحان السيناريوهات عادات تبدو معقولة، ولهذا تشحن العيوب. واختيار الطبقة الصحيحة للإصلاح هو المهارة التي يقيسها الامتحان.

## 📐 كيف يعمل

### 🟢 أنماط الأسئلة
أربعة خيارات، وإجابة واحدة يمكن الدفاع عنها، ولا «كل ما سبق». وتأتي الأسئلة في خمسة أنماط:
- **قرار:** ماذا تفعل أولًا أو تاليًا في هذا الموقف؟
- **تشخيص:** أي سبب يفسر هذا العَرَض، وفي أي طبقة؟
- **دليل:** أي تقييم أو تتبّع أو سجل أو اختبار يمكن أن يفشل، وبذلك يُثبت شيئًا؟
- **تصميم:** أي نمط أو واجهة أدوات أو ضابط يناسب هذا المتطلب؟
- **مفاضلة:** أي خيار يناسب التكلفة وزمن الاستجابة والاستقلالية والمخاطرة في السيناريو؟

### 🟡 الاستبعاد
اقرأ السطر الأخير أولًا، ثم السيناريو. اشطب الخيارات التي لا تجيب عن السؤال المطروح. ثم احذر الاختصارات التي يلجأ إليها الممارسون فعلًا: موجّه أطول، ونموذج أكبر، و«اخفض درجة الحرارة» وهو ما لا تستطيع ضبطه في الغالب على النماذج الحالية، ووكيل آخر، وقاعدة في موجّه النظام تُستخدم ضابطًا، وإعادة المحاولة حتى ينجح، أو كلمة مطلقة حيث يقول الدرس إن الأمر يعتمد. قارن الخيارين الأخيرين بتفاصيل السيناريو: من المتضرر، وما الدليل الموجود، ومن يملك القرار.

> *السيناريو:* يستشهد نجم ديسك بوثيقة سياسات لم تُعطَ له قط. *الخيارات بصياغة مختصرة:* خفض درجة الحرارة؛ وإضافة «لا تختلق استشهادات أبدًا» إلى الموجّه؛ وفحص كل استشهاد مقابل المعرّفات المسترجعة في الشيفرة وحجب الإجابة؛ والضبط الدقيق على إجابات مستشهَد بها. *الاستبعاد:* درجة الحرارة في الغالب ليست لك لتضبطها على النماذج الحالية ولن توقفه؛ وسطر الموجّه طلب لا ضابط؛ والضبط الدقيق بطيء وغير مقاس. والفحص في الشيفرة وحده يفشل لسبب صحيح.

### 🔴 قراءة السيناريو
اسأل أربعة أسئلة عن كل نص سؤال. **من المتضرر وكيف؟** بيانات الموظفين، أو إجابة سياسة خاطئة، أو كتابة غير مؤكدة، أو فاتورة. **أي طبقة فشلت؟** استدعاء النموذج، أو التطبيق المحيط به، أو حلقة الوكيل، أو أعمال التسليم أو الإنتاج. **ما أرخص ضابط يمكن أن يفشل لسبب صحيح؟** فحص في الشيفرة، أو حالة تقييم، أو حقل تتبّع. **أي كلمة تحدّ من الإجابة؟** «أولًا»، أو «الأفضل»، أو «الأرجح»، أو «قبل». ولا تفترض وقائع لا يذكرها نص السؤال.

## 🛠️ التمارين
- 🟢 **راجع أخطاءك.** لا حاجة إلى واجهة برمجة. أحصِ كل سؤال خاطئ أو مخمَّن بحسب وسم الطبقة في الجدول أعلاه، وصنّف كلًا منها «لم أكن أعرف» أو «أسأت القراءة» أو «أغراني». *يكتمل عندما:* تستطيع تسمية وسميك الأضعف والعادة وراء كل منهما، ويكون لكل خطأ درس تعيد قراءته.
- 🟡 **اكتب خمسة أسئلة من عندك.** لا حاجة إلى واجهة برمجة. اختر وسمك الأضعف. اكتب خمسة سيناريوهات بصيغة الامتحان، لكل منها إجابة واحدة يمكن الدفاع عنها وثلاث إجابات خاطئة مغرية وتفسير ينتهي بوسمه ودرسه. *يكتمل عندما:* يجيب زميل عن الخمسة كلها، ويُحسم كل خلاف في تفسيرك، ولا يكون الخيار الصحيح هو الأطول دائمًا.
- 🔴 **درِّس درسًا واحدًا.** دون اتصال على النسخة المحاكاة، التي تُظهر الآليات لا الجودة. درِّس الدرس الكامن وراء وسمك الأضعف لزميل في 20 دقيقة، مع تشغيل واحد يفشل ثم ينجح من عدّة المختبر. *يكتمل عندما:* يستطيع الزميل أن يذكر القاعدة الرئيسة للدرس وزوجًا واحدًا من الضعيف مقابل القوي بكلماته، وتكون قد أعدت كل ما عجزت عن الإجابة عنه.

## ⚠️ أخطاء وفخاخ
- **التحقق من الإجابات أثناء الحل.** تتعلم إجابة واحدة وتفقد مقياس الباقي. أجب عن الستين كلها ثم تحقق.
- **الاكتفاء بعدّ الدرجة.** درجة جيدة مع تخمينات كثيرة تخفي ثغرات. راجع التخمينات كأنها أخطاء.
- **إعادة القراءة بدل الممارسة.** التفسير يصلح إجابة واحدة؛ أما تمرين الدرس فيبني التقدير المهني. أعد تنفيذه.
- **معاملة هذا الامتحان على أنه نسخة تجريبية من امتحان شهادة.** إنه يتبع هذه الدورة لا منهج أي امتحان. استخدم أدلة الجهة المانحة نفسها للحصول على شهادة.

## 🧾 الخلاصة
- اجلس للامتحان بكتاب مغلق في جلسة واحدة، وضع علامة «متأكد» أو «تخمين» على كل إجابة.
- اقرأ كل نص سؤال بحثًا عمّن تضرر وأي طبقة فشلت وأرخص ضابط والكلمة المحدِّدة.
- سجّل كل خطأ بحسب وسم الطبقة والدرس ونوع الخطأ: لم أكن أعرف أو أسأت القراءة أو أغراني.
- أعد تمارين دروسك الأضعف، ثم أعد الامتحان بعد أسبوعين على الأقل.

**15. يردّ TicketHub أحيانًا بالخطأ 503 لبضع ثوانٍ. تعيد حلقة لجين الخطأ إلى النموذج على هيئة نتيجة `is_error` وتترك له القرار. تُظهر تتبّعات مها تشغيلات تستدعي الأداة مرة بعد مرة حتى حدّ الخطوات (step cap)، وكل استدعاء يعيد إرسال السجل كاملًا. أي تغيير يناسب؟**

**16. في العرض التوضيحي النهائي تُعدّ لجين شريحة تقول «صحة الإجابات: 96 بالمئة على 50 حالة». يأتي الجدول من تشغيل غير متصل على المحاكي (mock) الخاص بحزمة المختبر (lab kit)، إذ لا توجد ميزانية لتشغيل حقيقي قبل يوم الخميس. وستكرر هند الرقم أمام اللجنة. ماذا ينبغي أن يطلب فهد منها أن تفعل؟**

- C. الإبقاء على الرقم مع إضافة أن البوابة غير المتصلة نجحت مقابل خط الأساس (baseline)، وهو ما يعني غياب الانحدار

</details>

**17. تسأل يارا نجم ديسك: «ما تقدّم التذكرة 4471؟» فيجيب من المعرفة العامة ولا يستدعي `get_ticket_status` أبدًا، وهي أداة يقول وصفها: ⁦"Gets ticket info."⁩ أي تغيير هو أفضل إصلاح أول؟**

**18. يوم الخميس يبدأ سكربت التقييم لدى لجين بالفشل على واجهة البرمجة الحقيقية بالخطأ 429 الذي تقول رسالته إن حد الإنفاق للمؤسسة قد بُلغ. لا تحمل الاستجابة ترويسة `retry-after`، وقد أعادت حزمة التطوير (SDK) المحاولة مرتين. ماذا ينبغي أن تفعل؟**

- B. إضافة مزيد من عمليات إعادة المحاولة (retries) بالتراجع الأسي (exponential backoff) مع التشويش (jitter) حول استدعاء الواجهة
- C. خفض `effort` ليصبح كل استدعاء أرخص ثم إعادة تشغيل السكربت
- D. إنشاء مفتاح واجهة برمجة جديد، لأن المفتاح القديم هو الذي بلغ الحد

<details><summary>الإجابة</summary>

**A.** الخطأ 429 الذي يسمّي حد الإنفاق ولا يحمل `retry-after` ليس حدًّا عاديًا للمعدل: فلا يزول إلا برفع الحد أو إصلاح الفوترة أو إعادة ضبط الفترة، ولذلك فإن إعادة محاولات الحزمة وأي تراجع أسي (backoff) من عندها لا تفعل إلا تكرار الفشل. أما الاستدعاءات الأرخص فما زالت مرفوضة، والحد يخص المؤسسة أو مساحة العمل لا مفتاحًا واحدًا. *(Delivery · 0.2)*

</details>

**C.** قد تمارس الاختبارات الخضراء المحاكي أو لا شيء على الإطلاق، والدليل يتفوق على ملخص الوكيل نفسه؛ وكسر الكود عمدًا يُظهر ما إذا كان الاختبار قادرًا على الفشل. إعادة التشغيل تُظهر الاستقرار لا القوة، وترتيب الكتابة لا يجعل الاختبار حساسًا. *(Delivery · 0.3)*

**30. يقول موجّه نجم ديسك: «أجب من وثائق السياسات فقط». وحين يُسأل هل يجوز اصطحاب حاسوب العمل المحمول إلى مؤتمر في الخارج، ولا تغطي ذلك أي وثيقة، يخترع قاعدة بثقة. أي تغيير هو الأفضل؟**

- A. رفع `effort` ليتحقق النموذج من الوثائق بعناية أكبر قبل أن يجيب
- B. إخباره بأن يبدأ بـ `HANDOFF:` حين تصمت الوثائق، مع مثال واحد
- C. وضع ⁦"NEVER make anything up!!!"⁩ بحروف كبيرة في أعلى الموجّه
- D. إضافة خمسة أمثلة أخرى على أسئلة سياسات أُجيب عنها إجابة صحيحة

<details><summary>الإجابة</summary>

**B.** يسمّي الموجّه مصدر الحقيقة (source of truth) لكنه لا يمنح مخرجًا مسموحًا، و"لا أعرف" يجب أن تكون إجابة مسموحة وإلا اخترع النموذج واحدة؛ فاكتب المخرج صراحة، وأره في مثال، واختبره على أسئلة بلا جواب. يغيّر الجهد (effort) مقدار تفكير النموذج، لا القاعدة الناقصة؛ والتشديد بالصراخ يُفرط في التطبيق؛ والأمثلة التي تُجيب كلها تعلّم الأسلوب لا المخرج. *(Applications · 2.1)*

</details>

**31. تريد نورة أن يفحص ثلاثة مراجعين مستقلين كل بريد إلكتروني مُبلَّغ عنه، يحكم كل منهم على سؤال «هل يبدو هذا تصيّدًا احتياليًا؟»، ويُوسَم البريد إذا قال أي منهم «نعم»، حتى لا تُمرِّر نقطة عمياء واحدة رسالة تصيّد. تنوي لجين إرسال الموجّه نفسه إلى النموذج نفسه ثلاث مرات ووسم البريد إذا قال أي استدعاء نعم. ماذا ينبغي أن تفعل بدلًا من ذلك؟**

- A. إرسال الموجّه نفسه ثلاث مرات على التوالي ليبني كل استدعاء على الحكم السابق
- B. أن يُطلب من استدعاء واحد أداء دور ثلاثة مراجعين وإرجاع أحكامهم الثلاثة معًا
- C. الإبقاء على الخطة، لأن الاستدعاءات المتكررة لموجّه واحد تمنحك أصواتًا مستقلة على أي حال
- D. تشغيل ثلاثة استدعاءات جنبًا إلى جنب، لكل منها موجّه مختلف أو نموذج مختلف

**D.** درجة الحرارة (temperature) ليست في معظمها بيدك في النماذج الحالية، فتشترك الاستدعاءات المتطابقة في النقاط العمياء نفسها لموجّه واحد ونموذج واحد، وتميل إلى الاتفاق، وتزيد التكلفة دون أن تزيد التنوع؛ فيجب أن يختلف المصوّتون بالموجّه أو بالنموذج، ويُبقي تشغيلها معًا التأخير بمقدار أبطأ استدعاء. C هي الخطة المغرية. و B استدعاء واحد لا ثلاثة آراء، و A تجعل الأصوات اللاحقة تعتمد على السابقة. *(Applications · 5.1)*

</details>

**32. في الأسبوع 3، والبناء في مرحلة M5 جارٍ، ترسل هند إلى لجين: «هل يستطيع نجم ديسك أيضًا التعامل مع إعادة تعيين كلمات المرور؟ الموظفون يسألون عنها باستمرار.» كان المقترح وخطة الإطلاق قد وُقِّعا في M4، وأُدرجت إعادة تعيين كلمة المرور خارج النطاق. ماذا ينبغي أن تفعل لجين؟**

**D.** بعد M4 يتحرك النطاق بطلب تغيير: تحليل أثر يبيّن ما الذي يتغير — المتطلب والأدوات والاستقلالية (autonomy) وتدفق البيانات (data flow) وسجلات القرار المعماري — ومن يجب أن يوافق، وما الدليل الذي يحتاجه، وكم يكلّف من جهد ومواعيد. إعادة تعيين كلمة المرور تغيير في النطاق وفي المخاطر، فتقرر هند النطاق كتابةً وتقرر ليلى أو نورة أو سارة المخاطر. و A تعديل سريع يتخطى التحليل. و B يبني أولًا ويسأل لاحقًا. و C متصلب، لأن العملية تسمح بالتغيير حين تكون كلفته معروضة على الطاولة. *(Delivery · 16.1)*

</details>

**33. تطلب هند قدرة جديدة: عندما يبلّغ الموظفون عن هاتف مفقود، يُعدّ نجم ديسك طلبًا لإلغاء وصول الهاتف إلى صندوق بريد البنك في Najm ID، ويوافق عليه موظف مكتب الخدمة. كيف ينبغي تحديد مستواها، وماذا يترتب على ذلك؟**

**34. وكيل لجين القائم على `claude-sonnet-5-5` يجيب عن أسئلة حالة التذاكر. خطواته لا تتغير أبدًا: يستدعي `get_ticket_status` ثم يكتب الرد. لا يفعل شيئًا غير ذلك، وفي التتبّعات يتخطى الاستدعاء أحيانًا. ما التصميم الأفضل؟**

**35. في فريق المختبر، يطرح موظف سؤالًا لا تتناوله مكتبة السياسات. يعود الباحث بلا نتائج ويسجّل الفجوة. ماذا ينبغي أن يفعل المشرف؟**

**37. تُرجع أداة لجين `lookup_ticket` النص `No ticket 9999 found` كنتيجة `is_error`. وفي التتبّعات يعتذر النموذج عن «عطل في النظام» ثم يستدعي الأداة مرة أخرى ثلاث مرات. ما التصميم الأفضل؟**

**A.** «لم يُعثر على شيء» بيانات يستطيع النموذج الإبلاغ عنها، بينما يشير `is_error` إلى أن الاستدعاء فشل — مهلة أو مدخل غير صالح أو أداة مجهولة — ويدعو إلى إعادة المحاولة أو الاعتذار. وحذف النتيجة خطأ 400 (a 400)، والاستثناء المتسرّب ينهي التشغيل كله، والحدّ الأعلى لا يدفع إلا ثمن تكرارات أكثر. *(Agents · 3.2)*

**38. في المختبر، يرفض نجم ديسك الأداة `remember` لبقية الجلسة بمجرد أن يقرأ الوكيل ملاحظة تذكرة، حتى عندما يطلب المستخدم منه الاكتفاء بـ«إجابات قصيرة». تسمّي يارا هذا خللًا، لأن الملاحظة لم تقل سوى «انحشار في الطابعة بالطابق 3». ما الرد الصحيح؟**

**A.** القاعدة تخص المصدر لا المحتوى: فالكذبة المصوغة كأنها حقيقة تبدو غير ضارة لأي فحص للصياغة، ويبقى نص الملاحظة في السياق لبقية الجلسة. ويمكن الالتفاف بالكلام على المصنِّف أو على حكم النموذج نفسه، ولا تزيل رسالة المستخدم التالية نصَّ شخص غريب من السياق. *(Agents · 9.2)*

**39. أثناء حمل زائد استمر 40 دقيقة لدى المزوّد، يجري غلاف نجم ديسك حتى ثلاث محاولات لكل طلب مع فترات انتظار متذبذبة عشوائيًا ثم يجيب من النموذج الاحتياطي (fallback model). يتأخر الآن كل طلب نحو عشر ثوانٍ قبل أن يجيب النموذج الاحتياطي. ما الذي ينقص؟**

**40. لدى وكيلي الكاتب والمراجِع في نجم ديسك سقف 5 خطوات لكل دور. في الإنتاج استغرق سؤال واحد 46 استدعاءً للنموذج: ظل المراجِع يرفض المسودة بالاعتراض نفسه وظل الكاتب يعيد تقديمها. أي تغيير يعالج السبب؟**

- B. الموافقة على المسودة تلقائيًا بعد أن يرفضها المراجِع ثلاث مرات

**D.** التزم كل وكيل بحدّه الخاص؛ لكن لم يكن شيء يحدّ الفريق. والمشرف، وهو شيفرة عادية، يملك حدّ الجولات والميزانية والموعد النهائي وقاعدة عدم إحراز التقدم — المشكلات نفسها مرتين — وتُرسل حزمة إلى شخص حين تنطلق إحداها. وخفض حدود الخطوات (step caps) يحدّ الدور الواحد لا عدد الأدوار؛ والموافقة التلقائية تُمرِّر المسودة التي رفضها المراجِع؛ ويمكن للمشرف الذي يعمل بنموذج أن يقرر المواصلة إلى ما لا نهاية. *(Agents · 11.1)*

**41. لدى فريق نجم ديسك مجموعة تقييم ببوابة تكامل مستمر (CI gate)، ودليل تشغيل (runbook) بجدول مناوبة. بعد محادثة سيئة واحدة يوم الأحد، تسأل مها ماذا فعل الوكيل في تلك المحادثة ولماذا، ولا يستطيع أحد إعادة بناء ما حدث. أي خاصية بمستوى المؤسسات ناقصة، وما دليلها؟**

- A. قابل للمراقبة: تتبّع لخطوات كل محادثة واستدعاءات الأدوات ونتائجها
- B. موثَّق: مواصفة وسجلات قرارات ومخطط للتصميم
- C. موثوق: مهلات (timeouts) وإعادات محاولة محدودة وحدود للحلقة مع قاعدة توقف مختبرة

- D. الاحتفاظ بكائن حالة (state object) تحدّثه الشيفرة في كل خطوة وتضعه في كل موجّه

<details><summary>الإجابة</summary>

**D.** هذه ذاكرة عاملة (working memory): كائن الحالة من التذكرة والخطوات المجرَّبة وما يُنتظر تملكه حلقتك وتحدّثه في الشيفرة وتعرضه في المكان نفسه في كل موجّه، وهو رخيص وقابل للاختبار وجاهز للتسليم (hand-over). أما حفظ كل دور كما تقترح لجين فيحوّل حاجة بطول المهمة إلى عبء طويل الأمد؛ والملخص الذي يكتبه النموذج بيانات مشتقة قد تفقد الوقائع المهمة نفسها أو تخترعها، والنموذج الذي يعيد ذكر حالته بنفسه، أو قاعدة في الموجّه، رجاء لا ضابط. *(Agents · 9.1)*

</details>

**54. يرفض بوت السياسات لدى لجين، المعتمد على المتجهات وحدها، سؤال «في أي وقت تغادر الحافلة؟» لأن أيًّا من المقاطع لا يتجاوز `MIN_SIM`. فتضيف BM25 والدمج الهجين (hybrid fusion)، وترى الاستدعاء عند 3 (recall at 3) يرتفع على الأسئلة العشرة الموسومة، وتُطلقه. وفي التجربة التشغيلية يجيب البوت عن سؤال الحافلة من مقطع ساعات مكتب الخدمة. أي فحص يُجرى قبل الإطلاق كان سيلتقط هذا؟**

- A. أسئلة خارج الموضوع تُمرَّر عبر المسترجِع الهجين مع توقع جملة الرفض
- B. الاستدعاء عند 3 ومتوسط الرتبة المتبادلة (MRR) على الأسئلة العشرة الموسومة ضمن النطاق، وإعادة تشغيلها بعد التغيير
- C. مقيِّم الاستناد يُشغَّل على إجابات الأسئلة العشرة كلها ضمن النطاق
- D. الأسئلة نفسها خارج الموضوع تُمرَّر عبر المسترجِع القديم بالمتجهات وحدها الذي استبدلته

<details><summary>الإجابة</summary>

**A.** عتبة التشابه لا تقصّ إلا قائمة المتجهات. وقد يمرّر BM25 مقطعًا يشارك كلمة مثل «وقت»، فلا يفشل إلا حالة خارج الموضوع تُرسل عبر المسترجِع الذي تطلقه. يعيد D اختبار مسترجِع لم يعد مستخدمًا، ويقيس B وC أسئلة ضمن النطاق لا يمكنها أن تُظهر رفضًا مفقودًا. *(Applications · 4.2)*

</details>

**55. تريد شركة استشارات من 40 شخصًا أن يطرح موظفوها أسئلة عن دليلها المكوّن من 12 صفحة. يتغير الدليل مرتين في السنة، ويحق للجميع قراءته كله، ولا يحتاج أحد إلى استشهادات. يقترح مطوّر استخدام Chroma والبحث الهجين ومعيد ترتيب (reranker). ما أفضل تصميم أول؟**

- A. ضبط نموذج على الدليل وإعادة تدريبه بعد كل تعديل
- B. بناء التوليد المعزَّز بالاسترجاع (retrieval-augmented generation, RAG) بمخزن متجهات (vector store) وبحث هجين ومعيد ترتيب من اليوم الأول
- C. منح وكيل أداة بحث في الملفات وترك قرار الصفحات التي يقرؤها له
- D. لصق الدليل كله في الموجّه مع كل سؤال

<details><summary>الإجابة</summary>

**D.** جمهور واحد، ونص صغير ومستقر، ولا التزام بالاستشهاد: لصق المكتبة في الموجّه هو أبسط ما يعمل، ويمكن للتخزين المؤقت أن يخفض التكلفة لاحقًا متى تجاوزت البادئة الحد الأدنى للنموذج. والتوليد المعزَّز بالاسترجاع (RAG) يستحق مكانه حين تكون المكتبة كبيرة أو متغيرة أو ذات صلاحيات وصول أو يجب الاستشهاد بها؛ والضبط الدقيق (fine-tuning) وسيلة ضعيفة لإضافة الوقائع؛ والوكيل يضيف خطوات قد تفشل. *(Applications · 4.1)*

</details>

**56. تقدّر لجين نجم ديسك بستة إلى تسعة أسابيع للوصول إلى بناء جاهز للتجربة التشغيلية. أكبر مجهول لديها هو هل يعمل الاسترجاع على صفحات الإرشادات العربية في مكتب الخدمة، والمدى كله يعتمد عليه. ماذا ينبغي أن تفعل قبل إرسال التقدير؟**

- A. إضافة خمسين بالمئة إلى أعلى المدى كي يمتص نتيجة عربية ضعيفة
- B. إجراء تجربة استكشافية محدودة الوقت على الاسترجاع العربي ثم تحريك المدى ليناسب النتيجة
- C. إرسال المدى الآن وحسم مسألة العربية حين يكون البناء جاريًا
- D. إرسال رقم واحد من أعلى المدى كي لا تكون لديها فجوة تدافع عنها لاحقًا

<details><summary>الإجابة</summary>

**B.** التجربة الاستكشافية (spike) تجربة محدودة الوقت على أخطر مجهول؛ فإن كان معدل الاستدعاء ضعيفًا يتحرك المدى الآن، بينما لا يزال النطاق قابلًا للتغيير. يخفي A عدم اليقين داخل رقم منفوخ، ويترك C المفاجأة تصل في منتصف البناء، ويقدّم D رقمًا واحدًا، وعدًا لا يستطيع أحد الوفاء به. *(Delivery · 7.2)*

</details>

**57. في تشغيل اختبار قبول المستخدم يفشل الصف U-10: يطلب ريان فتح حساب مقفل، فيرد نجم ديسك بأنه فتحه، ويُظهر Najm ID أن الحساب تغيّر. ينص الصف على أن الطلب يجب أن يسمّي المدير وأن يترك Najm ID وشأنه. لدى هند موعد إطلاق وتعرض توقيع تنازل بمالك وتاريخ. ماذا تقول قواعد القبول؟**

- A. لا توقيع: الكتابة الخاطئة مانع، فأصلحها وأعد تشغيل كل صف قد يمسّه الإصلاح
- B. توقيع التنازل: يجوز للراعي أن يتنازل عن أي صف فاشل إن سمّى مالكًا وتاريخًا
- C. التوقيع مع تعليق: فتح الحسابات نادر، فيمكن للصف أن ينتظر في قائمة المهام المؤجلة لإصدار لاحق
- D. توقيع الصفوف التي نجحت وإرجاء U-10 إلى المرحلة التالية من الطرح

<details><summary>الإجابة</summary>

**A.** صف الحاجز الوقائي الفاشل أو الكتابة الخاطئة مانع. أما التنازل بمالك وتاريخ فمخصص لإخفاق جسيم ليس غير آمن، والإخفاق الطفيف يجوز أن يذهب إلى قائمة المهام المؤجلة. وبعد الإصلاح يُعاد تشغيل كل صف قد يمسّه. B هو الخيار المغري، ويعامل المانع كأنه إخفاق جسيم. ويحوّل C العيب إلى تعليق، ويوقّع D بناءً فيه كتابة غير آمنة معروفة. *(Delivery · 15.2)*

</details>

**58. يخدم نجم ديسك الكيانين القطري والإماراتي من مكدّس واحد. تصفّي لجين كل استعلام استرجاع بمعرّف المستأجر (tenant id) المأخوذ من الجلسة، ويجتاز اختبار المستأجرَين لنورة. ثم تضيف مها ذاكرة تخزين مؤقت للردود للأسئلة المتكررة عن السياسات، مفتاحها تجزئة نص السؤال. يسأل مستخدم من الإمارات ما سأله مستخدم من قطر قبل ساعة، فيقرأ إجابة كيان قطر. ما الحل؟**

- A. تقصير عمر الذاكرة المؤقتة إلى خمس دقائق كي يندر تقديم إجابة قديمة
- B. وضع معرّف المستأجر الخاص بالجلسة في مفتاح الذاكرة المؤقتة (cache key) ثم إعادة تشغيل اختبار المستأجرَين
- C. إضافة إصدار الموجّه إلى مفتاح الذاكرة المؤقتة (cache key) كي لا يقدّم أي إصدار إجابة موجّه أقدم
- D. مطالبة النموذج بتسمية المستأجر في كل إجابة وتخزين الإجابة مؤقتًا تحت ذلك الاسم

<details><summary>الإجابة</summary>

**B.** معرّف المستأجر من الجلسة مكانه في كل استعلام ومرشّح ومفتاح ذاكرة مؤقتة ومفتاح ذاكرة وحقل سجل. الذاكرة المؤقتة باب ثانٍ لا يحرسه مرشّح الاسترجاع أبدًا، وبعدئذٍ يثبت اختبار المستأجرَين ذلك. A يضيّق النافذة فحسب، وC يجعل المفتاح بحسب الإصدار وهو ممارسة جيدة لكنه يترك كيانين يتشاركان مفتاحًا داخل إصدار واحد. ويأخذ D المستأجر من النموذج بينما يجب أن يأتي من الجلسة. *(Production · 13.2)*

</details>

**59. في التجربة التشغيلية يوافق موظفو مكتب الخدمة على 99.8% من طلبات فتح الحسابات، عادةً خلال خمس ثوانٍ من ظهور الطلب، مع أن معاودة الاتصال بالمدير تستغرق 20 دقيقة أو أكثر. تقرأ هند ذلك دليلًا على دقة المساعد وتريد أن يجري فتح الحسابات بلا موافقة. ماذا يوصي به درس التصميم؟**

- A. إبقاء الموافقة، وإظهار دليل معاودة الاتصال للمعتمِدين، والرفض عند انتهاء المهلة، ومراقبة المعدل
- B. قبول قراءة هند وإسقاط الموافقة لأن الموظفين لن يوافقوا على طلب يبدو خاطئًا
- C. اشتراط موافقة موظف ثانٍ على كل طلب لأن نقرتين تلتقطان أكثر من نقرة واحدة
- D. استبدال الموافقة بثقة النموذج المعلنة لأن 99.8% يبيّن أنها معايَرة

<details><summary>الإجابة</summary>

**A.** موافقة شبه كاملة خلال ثوانٍ، قبل وقت طويل من إمكان انتهاء معاودة الاتصال، تعني أن الناس ينقرون ولا يراجعون. يبقى فتح الحساب طلبًا يوافق عليه شخص؛ والتحقق البشري يحتاج إلى دليل أمام المعتمِد وقاعدة الرفض عند انتهاء المهلة ومالك يراقب المعدل. B هو القراءة المغرية، ويضيف C نقرة ثانية بلا دليل إضافي، وثقة النموذج المعلنة ليست ضابطًا. *(Agents · 7.1)*

</details>

**60. مساء الخميس تطلب يارا من لجين إسقاط وثيقة سياسة «العمل من الخارج» الجديدة في المجلد الذي يفهرسه نجم ديسك كي تكون فعّالة في ذروة الأحد. «إنها محتوى لا شيفرة، فلا تحتاج إلى إصدار.» ولن تُظهر لوحة مها أخطاء في الحالتين. ماذا ينبغي أن تفعل لجين؟**

- A. فهرسته الليلة ومراقبة معدل الأخطاء صباح الأحد لأن الوثيقة لا تستطيع إسقاط الخدمة
- B. فهرسته لثلاثة من الموظفين الأربعة عشر لمدة ساعة ثم توسيعه إن بقيت لوحة مها هادئة
- C. فهرسته الليلة ثم تكليف يارا بقراءة بعض إجاباته يدويًا قبل ذروة الأحد
- D. تشغيل بوابة التقييم (eval gate) ومجموعة الفريق الأحمر (red-team set) عليه، وتسمية الفهرس الذي يُتراجع إليه، ثم الإطلاق على مراحل

<details><summary>الإجابة</summary>

**D.** محتوى الاسترجاع تغيير مثل الموجّه أو معرّف النموذج: قيّمه واختبره بالفريق الأحمر وسمِّ النسخة التي يُتراجع إليها ثم أطلقه على مراحل. يراقب A الإخفاقات الصاخبة بينما سيكون الإخفاق هادئًا. وB إطلاق مرحلي بلا بوابة ولا تشغيل هجومي ولا هدف تراجع، وإشارة التوقف الوحيدة فيه لوحة لا تُظهر أخطاء في الحالتين: الكناري الضعيف. أما C فمعاينة يدوية بلا مجموعة انحدار (regression set) ولا هدف تراجع. *(Production · 15.1)*

</details>
