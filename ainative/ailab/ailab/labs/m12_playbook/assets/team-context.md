# Payments Platform: the facts your playbook may rely on

Everything in this file is fictional and was written for the course. Your playbook may rely on it and
must not contradict it. Do not edit this file.

## The team
- **Payments Platform** owns Najm Remit: 8 engineers, 2 of them in their first year.
- **Tariq**, engineering lead, runs the weekly AI-native clinic and will own the playbook. **Hessa**
  writes the tickets. **Nada** owns test strategy. **Noura** owns application and AI security. **Maha**
  leads SRE, incidents and on-call. **Salem** runs CI and the approved-tools list. **Sara** is the data
  protection officer, **Layla** heads AI governance and **Hamad** is the CISO.

## The bank's AI-engineering rules (they bind every team)
1. Only approved tools, run in approved environments.
2. No Confidential or Restricted data and no secrets in prompts or agent contexts.
3. AI-written code is reviewed like any other, and the author remains accountable.
4. Agents run with least privilege and never touch production.
5. Changes to money logic need a second human reviewer.
6. Every AI-assisted change is labelled in the pull request.

## Data classes (Sara)
Public, Internal, Confidential, Restricted. The Remit source code is Internal. Customer names, account
numbers, transfer histories, production logs and the sanctions watchlist are Restricted.

## Approved tools (Salem's list)
Claude Code on the bank's enterprise account, signed in through SSO; GitHub Copilot in the IDE, on the
enterprise plan. Nothing else is approved. Personal accounts and free tiers never are. A new tool starts
as a request to Salem, who asks Noura for a security review and Sara for a data review.
