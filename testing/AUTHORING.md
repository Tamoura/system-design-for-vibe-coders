# Software Testing: Zero to Hero in the AI Era — authoring guide

This is the contract every lesson follows. It is not published.

## What the course is

A free, bilingual (English/Arabic) course that takes a reader from zero to "hero" in **proving that software works — and finding out quickly and cheaply when it does not** — in a world where AI coding agents write much of the code, AI tools can help write and run tests, and many products now contain AI components whose behaviour is probabilistic.

Three AI-era threads run through the whole course (not only Modules 6–7):
1. **Testing code that an AI wrote.** More code, written faster, by a builder that is fluent and confidently wrong. The reader's job shifts from typing tests to *judging evidence*: are these tests able to fail? What do they actually pin down?
2. **Using AI to test.** Test ideas, test data, generated tests, agentic test runners, self-healing locators, failure triage — and their limits (plausible but vacuous tests, privacy, cost, vendor claims).
3. **Testing AI systems.** LLM apps, RAG, tool-using agents: non-determinism, no single correct answer, evals, LLM-as-judge, safety and bias testing, monitoring and drift.

- **Audience:** computer science, data science and computer/software engineering graduates aiming at QA, test-automation (SDET), quality-engineering or developer roles; developers and "vibe coders" who must verify what an agent produced; manual testers moving into automation; product, engineering and risk staff at GCC banks, government bodies and enterprises. Basic programming (Python or JavaScript) and a command line help; no testing experience assumed.
- **Hands-on and free to practise.** Primary languages: **Python (pytest, Hypothesis)** and **TypeScript/JavaScript (Playwright, Vitest or Jest)**; mention Java/JUnit and others where they are the industry default. Exercises run on a laptop: pytest, Hypothesis, a mutation tester, Playwright, k6, Docker/Testcontainers, OWASP ZAP, and a **tiny hand-written fake "model" function or a local open-weight model** for the AI exercises — **no paid API key is ever required**; if a lesson mentions a hosted model API, tell the reader to set a spending cap first. Never run security or load tests against systems you do not own or have written permission to test.
- **Engineering judgement over tool tours:** every lesson leaves the reader able to make a testing decision (what to test, at which level, what is good enough, whether to ship) or produce an artefact (a test design, a test, a strategy, a gate).
- **Honest about AI and about tools.** No hype; no claim that AI replaces testers or that it cannot help. Vendor features and versions change — name what you are sure of, hedge the rest ("at the time of writing (2026)"). Never invent statistics, prices, benchmark scores, quotes, dates, URLs or version numbers.
- **Companion courses** (relative links; catalogue in `LIBRARY.md`): *System Design for Vibe Coders* (8.2 tests as the spec, 8.3 CI preflight, 9.4 verification before completion), *Cloud & DevOps* (4.1 CI, 4.2 safe releases, 5.1 telemetry, 5.2 SLOs), *Secure AI & Application Security* (6.1 SAST/DAST/SCA, 2.x web attacks, 9.4 AI red-teaming), *Data Engineering & Analytics* (3.1 dbt, 3.2 data quality), *AI Product Management* (6.1 golden sets and error analysis, 6.2 LLM-as-judge, 6.3 online evaluation), *AI Governance* (9.3 testing, evaluation, validation and red-teaming), *Running AI Agents in Production* (agent operations), *SaaS Building Blocks*, and *From Graduate to Hired* (1.1 the junior baseline; role paths). Point to them in one line where they go deeper, and stay on the *testing decision* here.

## The running case: Najm Bank's Quality Engineering team

**Najm Bank** is the fictional mid-sized Gulf bank (Qatar, the UAE and the EU) used across the library. Say it is fictional in lesson 0.3. Here we sit in its **Quality Engineering (QE)** team, embedded with the squads that build the products.

Systems under test (use consistently):
- **Najm Mobile** — the retail banking app (iOS, Android and web) in English and Arabic (right-to-left), and the **Najm Mobile API** behind it: login, accounts, **transfers** (own account, domestic, international), bill payments, card controls, beneficiaries, limits. The running feature in many lessons is **Transfers**: amounts, currencies (QAR, AED, EUR), daily limits, cut-off times and time zones, duplicate-submit protection, notifications.
- **Payments service** — must not lose, duplicate or mis-round a transfer; idempotency keys; strict recovery targets.
- **Najm Assist** — the LLM assistant: answers questions from bank policy documents (retrieval-augmented generation, RAG) and can call tools (read-only balance lookup; **freeze card** is a write action that needs explicit confirmation).
- **Regulatory reporting pipeline** — nightly data files to the regulator; data-quality checks.
- Environments: dev, QA/test, staging (production-like), production. Test data is synthetic or masked — never raw customer data.

## The shared sample system under test: Najm Transfers

All modules test the **same small fictional system**, so the course reads as one story and every snippet fits together. It lives in the repository at `testing/sample/` (GitHub: https://github.com/Tamoura/system-design-for-vibe-coders/tree/main/testing/sample — link it in lessons as "the course's sample system"). **Read `testing/sample/README.md` and the source files before you write.** Do NOT edit anything under `testing/sample/`; for experiments copy it to your scratch dir (`cp -r testing/sample /home/user/coursework/scratch/<module>/`).

- `najm/transfers.py` — `quantize(amount, currency)`, `fee(amount, currency, kind)`, `check_transfer(amount, currency, kind, sent_today)` → `Decision(fee, total)` or raises `TransferRejected(code)` (codes: `unsupported_currency`, `unsupported_kind`, `too_many_decimals`, `below_minimum`, `above_per_transfer_max`, `daily_limit_exceeded`), `value_date(now, tz)` (15:00 Qatar cut-off, Friday/Saturday weekend), `TransferService` (idempotency keys, ownership, balances). Rules: min 1; max 25,000 QAR/AED or 5,000 EUR per transfer; daily limit 50,000 QAR/AED or 10,000 EUR; fees: own free, domestic free up to 1,000 then 2.00, international 0.35 % (min 10.00, max 100.00); half-up rounding.
- `najm/api.py` — `create_app()` (use a fresh app per test), endpoints `POST /transfers` (needs `Authorization: Bearer token-alice|token-bob` and `Idempotency-Key`; 201 created, 200 replay with `Idempotent-Replay: true`, 400/401/403/409/422), `GET /transfers/{id}`, `GET /accounts/{id}/balance`, `GET /health`, `GET /app` (HTML page).
- `static/transfer.html` — labelled form (From account, Recipient account, Amount, Currency, button "Send transfer"), result in `role="status"` / `role="alert"`; `?lang=ar` gives the Arabic right-to-left version.
- `najm/assist.py` — Najm Assist stand-in: `POLICY_DOCS`, `retrieve(query, k)`, `FakeModel(temperature, seed)`, `answer(question, model)`, `Agent` with tools `get_balance` and `freeze_card` (confirmation required).
- **Seeded bugs** switched on by environment variables `NAJM_BUGS` (`limit_off_by_one`, `float_fee`, `tz_cutoff`, `no_idempotency`, `bola`) and `NAJM_AI_BUGS` (`hallucinate`, `obey_injection`, `skip_confirm`, `wrong_account`) — use them to show a test *failing for the right reason* and to measure a suite. A concrete worked bug: `fee("3090", "QAR", "international")` must be `10.82` (10.815 rounds half up); the `float_fee` bug returns `10.81`.
- `tests/` is a deliberately incomplete starter suite (it passes clean and catches only some seeded bugs); `e2e/` has a Playwright starter.

When a lesson needs code beyond the sample (a new test, a helper), show it in full and make sure it runs against the sample. Exercises should use the sample system wherever they can ("copy `testing/sample/`, then…"). Lessons in Modules 0–1 and 8.2 that need no code may refer to the sample only in passing.

## Facts to get right (and how to hedge)

State only what you are confident is true; name versions only when sure; hedge anything that changes "at the time of writing (2026)"; never invent statistics, prices, benchmark numbers, quotes or dates. If unsure of a deep link, link the project's top-level page.

- **Terminology & fundamentals (ISTQB CTFL v4.0, 2023; ISO/IEC/IEEE 29119):** error (mistake) → defect (bug, fault) → failure; verification ("are we building it right?") vs validation ("are we building the right thing?"); test oracle; the **seven testing principles** (testing shows the presence of defects, not their absence; exhaustive testing is impossible; early testing saves time and money; defects cluster; tests wear out — the pesticide paradox; testing is context dependent; absence-of-defects fallacy); test levels (component, component integration, system, system integration, acceptance); test types (functional, non-functional, black-box, white-box, change-related: confirmation and regression); static testing (reviews, static analysis) vs dynamic; test process activities (planning, monitoring and control, analysis, design, implementation, execution, completion). ISO/IEC 25010 product-quality model (functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability, portability; the 2023 revision renames/extends some characteristics, e.g. adds safety — hedge). "Testing vs checking" (Michael Bolton, James Bach) is a useful distinction; present it as one school's view.
- **Test design:** equivalence partitioning, boundary value analysis (2-value and 3-value), decision tables, state-transition testing, pairwise/combinatorial testing (tools such as PICT or `allpairspy`), use-case/scenario testing, error guessing, checklists, exploratory testing; experience-based techniques. Test-case anatomy (id, objective, preconditions, steps, data, expected result); Given/When/Then; defect lifecycle; severity vs priority; a good bug report (title, environment, steps, expected vs actual, evidence, minimal reproduction).
- **Domain traps worth teaching with Najm examples:** money as integers or decimals, never binary floats; rounding rules; currencies with different minor units (QAR/AED 2 decimals, KWD/BHD/OMR 3 decimals — fact: the Kuwaiti, Bahraini and Omani currencies use three decimals; JPY 0); time zones and DST (Gulf states have no DST; the EU does), cut-off times, leap days, month ends; Unicode, Arabic shaping and bidirectional text, Arabic-Indic digits, Hijri vs Gregorian dates; duplicate submits and idempotency keys; concurrency and race conditions.
- **Unit & integration testing:** arrange-act-assert; FIRST (fast, isolated/independent, repeatable, self-validating, timely); test doubles per Meszaros/Fowler (dummy, stub, spy, mock, fake); *state vs interaction* testing; TDD red-green-refactor (Kent Beck, *Test-Driven Development: By Example*, 2002); pytest (fixtures, parametrize, markers), unittest, JUnit 5, Vitest/Jest; `freezegun`/clock injection; the **test pyramid** (Mike Cohn; Martin Fowler's "Test Pyramid" and Ham Vocke's "The Practical Test Pyramid"), the **testing trophy** (Kent C. Dodds) and the **honeycomb** (Spotify, microservices) as differing emphases; Google's small/medium/large test sizes (*Software Engineering at Google*, 2020); Testcontainers (real databases in containers); in-memory fakes; test data builders/factories; test isolation (transaction rollback, unique data); **consumer-driven contract testing** (Pact, Pact Broker "can-i-deploy"), schema/OpenAPI-based contract checks; service virtualisation (WireMock, MockServer).
- **Test quality:** line vs branch coverage (coverage.py, JaCoCo, Istanbul/c8); coverage shows what code is *not* exercised, not that behaviour is verified (Goodhart's law); **mutation testing** (PIT for Java, Stryker for JS/TS/.NET, `mutmut` for Python), mutation score, equivalent mutants, cost (run on changed code); **property-based testing** (QuickCheck by Claessen & Hughes, 2000; Hypothesis for Python; fast-check for JS; jqwik for Java) — properties such as round-trip, idempotence, invariants, oracle comparison; shrinking; approval/snapshot/golden-master/characterisation tests (Michael Feathers, *Working Effectively with Legacy Code*, 2004) and the danger of "update snapshots until green"; **flaky tests**: causes (async timing, shared state, order dependence, time/randomness, network, concurrency, environment), fixes, detection by repeated runs, a quarantine policy with an owner and a deadline — retries hide flakiness and must be reported.
- **API testing:** HTTP methods and status-code classes; idempotency (PUT/DELETE idempotent by definition; POST needs an idempotency key); schema validation (OpenAPI / JSON Schema); pagination, filtering, versioning; auth (API keys, OAuth 2.0 bearer tokens, expired/forged tokens, scope checks), BOLA/IDOR (point to *Secure AI* 3.3 and 4.1); negative and boundary cases; rate limits; tools: pytest + `httpx` or `requests`, Postman/Newman, Bruno, REST Assured, Karate, Hurl, **Schemathesis** (property-based API testing from OpenAPI); GraphQL and gRPC exist (one line each).
- **UI / end-to-end:** **Playwright** (Microsoft; Chromium, Firefox and WebKit; auto-waiting; web-first assertions that retry; role- and text-based locators; browser contexts for isolation; trace viewer; codegen; `@playwright/test` runner with parallel workers and `--shard`), **Selenium** (W3C WebDriver standard), **Cypress**, WebdriverIO; Testing Library's "query by role" philosophy; **page object model** and its alternatives (fixtures, component objects, screenplay); never `sleep` — wait on conditions; test isolation (fresh login via API/storage state); visual regression (Playwright screenshots, Percy, Chromatic, Applitools — examples); component testing; E2E suites stay small and focus on critical journeys (Google's testing blog argued against over-reliance on end-to-end tests).
- **Mobile, accessibility, localisation:** Appium (WebDriver-based), Espresso (Android), XCUITest (iOS), Maestro, Detox (examples); real devices vs emulators; device clouds (BrowserStack, Sauce Labs, Firebase Test Lab — examples); network conditions, interruptions, permissions, OS upgrades, app-store review; **WCAG 2.2** (W3C Recommendation, October 2023; levels A/AA/AAA; the four principles perceivable, operable, understandable, robust), automated checks catch only a portion of issues (axe-core, Lighthouse; no invented percentage — say "a minority to roughly half" at most, or just "only some"), manual checks with a screen reader (NVDA, VoiceOver, TalkBack), keyboard-only, zoom/contrast; **i18n/l10n testing**: pseudo-localisation, text expansion, RTL mirroring (logical CSS properties, `dir="rtl"`), bidirectional text with embedded LTR (numbers, English brand names), Arabic shaping/fonts, Arabic-Indic vs Western digits, date/number formats, Hijri calendar, sorting/collation, plural rules (Arabic has six plural categories — true per CLDR: zero, one, two, few, many, other).
- **Performance:** load, stress, spike, soak (endurance), scalability, volume tests; **k6** (Grafana Labs; JavaScript scripts; thresholds, scenarios), JMeter, Gatling, Locust, Artillery; **percentiles (p50/p95/p99), not averages**; throughput vs latency vs error rate; open vs closed workload models; think time and ramp-up/warm-up; **coordinated omission** (Gil Tene); Little's Law (L = λW); production-like environment and data; performance budgets / SLO thresholds as pass–fail; client-side: Core Web Vitals (LCP, INP, CLS; INP replaced FID in March 2024), Lighthouse. - **Security testing for testers:** OWASP Top 10, **OWASP ASVS** (Application Security Verification Standard), **OWASP Web Security Testing Guide (WSTG)**; SAST (Semgrep, CodeQL, SonarQube), DAST (OWASP ZAP, Burp Suite), SCA / dependency scanning (OSV-Scanner, Trivy, Dependabot, `npm audit`, `pip-audit`), secret scanning, fuzzing (libFuzzer, AFL++, Atheris, Jazzer; property-based tests as "friendly fuzzing"), authorisation test matrices (role × resource × action), session and token tests, input-validation tests, security regression tests from every vulnerability; always get written authorisation; point to *Secure AI* 6.1, 3.3, 4.1.
- **Reliability & data:** chaos engineering (Netflix Chaos Monkey ~2011; "Principles of Chaos Engineering"; Chaos Mesh, LitmusChaos, AWS Fault Injection Service — examples), game days, failover and restore drills ("a backup is not a backup until restored" — GitLab 2017), timeouts/retries/circuit breakers tested with fault injection (Toxiproxy), schema migrations (expand–contract / backward-compatible changes, rollback tests, migration rehearsal on production-sized copies), data-quality tests (not null, unique, accepted values, relationships, freshness, volume, reconciliation; dbt tests, Great Expectations, Soda — point to *Data Engineering* 3.2), data masking and synthetic test data (Faker; point to privacy duties and *Secure AI* 5.3).
- **Strategy & delivery:** risk-based testing (risk = likelihood × impact; rank features, test depth follows risk); test strategy (the approach) vs test plan (the project-level detail); entry/exit criteria; definition of done; **Agile testing quadrants** (Brian Marick; Lisa Crispin & Janet Gregory, *Agile Testing*, 2009); shift-left and shift-right; **testing in production** (feature flags, canary releases, synthetic monitoring, observability — never as a substitute for pre-production tests; point to *Cloud & DevOps* 4.2, 5.1); quality metrics: defect escape rate, change failure rate and the other **DORA** metrics (hedge names), flake rate, time-to-feedback, mean time to detect/restore, requirement coverage — avoid vanity metrics (test count, raw coverage targets, "bugs found per tester"); test management tools (Jira, Xray, TestRail, Zephyr, Azure DevOps Test Plans — examples); reporting (Allure, built-in HTML reports); CI: stages, fast feedback, parallelism/sharding, caching, ephemeral environments, test selection (predictive/test-impact analysis — Meta published "Predictive Test Selection", 2018/19; hedge), flaky-test dashboards; contract tests gate deployments. - **AI-era: AI-generated code and tests (Modules 6.1–6.2):** coding agents (Claude Code, Cursor, GitHub Copilot's agent mode, OpenAI Codex — examples; no version claims) fail in characteristic ways: plausible-but-wrong logic, missed edge cases, **hallucinated APIs and packages** (and "slopsquatting" — attackers registering names models tend to invent; hedge as widely discussed), silent deletion or weakening of code and tests, over-mocking, tests that restate the implementation, tests with no or always-true assertions, snapshot updates "to make CI green", fixing the test instead of the code, coverage-gaming, security flaws (point to *Secure AI* 6.3), dependency bloat, inconsistent style. ## Quiz quality rules (every ✍️ block and the exam)

- Exactly one clearly correct option, defensible from the lesson; three distractors that are plausible mistakes practitioners really make (often the tempting shortcut). No "all/none of the above", no "Which is NOT".

- Test judgement and application in scenarios, not trivia or wording recall.
